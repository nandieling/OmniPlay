# 1.22：刮削结果回到海报墙，详情页补「手动匹配」与「自定义编辑」

## 详情页已刮削，首页还在原地

首页那面墙从来不是每次都问数据库，它渲染的是内存里的 `libraryItems`。刮削在后台线程推进，进度回调链上的补卡动作有两道闸：`screen != Screen.HOME` 直接丢弃，以及两秒一次的节流。用户的动作恰好把两道闸都踩上——点海报进详情页（第一道闸关掉），刮削在背后跑完；退出详情页时 `showHome()` 的这段：

```java
if (!returningFromDetail || !hasVisibleLibrary) {
    refreshHomeLibrary(!hasVisibleLibrary);
}
```

从详情页返回、库里又有东西，两个条件都不成立，于是只拿旧名单重绘，不重读。详情页是每次现查数据库的，就形成了「详情页写着已刮削、首页还是占位字母 + 整串文件名」。

现在 `showHome()` 在重绘之后无条件补一次 `refreshLibraryInPlace()`：后台重读媒体库、就地补卡片，卡片自己的渲染签名（片名 / 年份 / 观看进度 / 评分 / 海报 id）没变的仍然什么都不做，所以不会多出一次整墙重排。它同时管住另一件早就存在的事——看完片退出播放器，进度条也该跟着更新。

`patchLibraryViews()` 顺带修一处判据。它以前只比新旧两次读取的**条目数量**，数量相同就当「还是那批条目」，于是逐张按 id 补数据。清库重扫、手动匹配跨类型改绑（电影 ↔ 剧集换表重建实体，条目 id 变了）这两种情况下数量正好一样，每张卡都按旧 id 找不到对应的新条目，`libraryItems` 却被悄悄换成新名单，整面墙就再也不动了。现在比 id 集合：

```java
if (!byId.keySet().equals(distinctLibraryIds(libraryItems))) {
    libraryItems = items;
    scheduleWallRebuild();
    return;
}
```

## 手动匹配

mac 版是 `MovieSearchModalView`（源文件名 + 关键词 + 年份 + 结果列表 + 「关联此项」），这版是它的遥控器形态：

- 弹层显示源文件路径、关键词（预填当前片名）、年份，打开即搜一次——遥控器上打字是奢侈品，先按现有名字试一次比让用户按六次方向键去点「搜索」合适。
- 候选清单走新的 `TmdbClient.searchCandidates()`：与自动刮削同一份 `/search/multi` 取数、同一套 `score()` 打分（原片名匹配、次要查询、类型偏好、年份容差），只是不取最高分那一个，而是按分数从高到低整份列出（上限 24 条）。
- 每行是片名 + 「年份 · 类型 · 简介前 46 字」，点一行即关联；底部是 关闭 / 手机输入 / 搜索，关键词和年份都能用手机传。
- 关联走 `LocalEngine.bindToTmdbResult()`：写元数据、按 `append_to_response=credits` 补导演主演（名单已有内容就不覆盖，那可能是用户手填的），置 `isLocked = 1`，再 `showDetail()` 整页重开 + 刷新首页。
- 类型对不上时（文件名被当成电影扫出来、其实是一部剧集）`LocalMediaLibrary.applyManualMatch()` 换一张表重建实体、把 `videoFile` 行搬到新条目、删掉旧条目和它的队列行 / 分集行，返回新的实体 id。

## 自定义编辑

原来的「编辑」只有一格片名，换成 mac 版手动编辑资料的字段集：片名、上映日期、TMDB 评分、类型、导演、主演。名单输入用顿号 / 逗号 / 分号分隔，入库前统一转成库里那套竖线分隔；评分越界按 0–10 夹住，填了非数字就提示不保存。按钮写「保存修改并锁定」，与 mac 同名。六个字段都挂在「手机输入」上，长串演员名单不用拿遥控器一个字母一个字母戳。

两颗按钮放在播放按钮下面第二行：第一行原本已有 播放 + 观看状态，再塞一颗在 1080p 上就顶到边了，第二行也让左右走位短一截。

## 锁定开始真的生效

`isLocked` 这一列以前只写不读，锁了等于没锁，下一轮刮削照样覆盖。现在 `LocalEngine.scrapePending()` 取到批次后先看锁，锁着就跳过（批次是在取的时候连行删掉的，跳过不会让「待刮削」下不去）。`requeueScrape()` 反过来先解锁：用户主动点重刮，要的就是新结果，不能被上一次的手动匹配挡着。

## 验到的

模拟器（`android-tv;android-34;arm64-v8a`，`-gpu host`）拿一台临时 HTTP 服务当 TMDB（反代填 `http://10.0.2.2:8099/tmdb`，返回固定的两条结果与一份 `append_to_response=credits`），好处是结果可控、也能看清 App 到底发了什么请求：

- 设置里保存反代后点「验证连接」，服务端收到 `GET /tmdb/3/configuration?api_key=…`，说明反代地址与 `/3` 补全这条链是对的。
- 详情页第二行是「手动匹配」「自定义编辑」两颗按钮。点手动匹配，服务端立刻收到 `GET /tmdb/3/search/multi?query=Film+01&language=zh-CN&page=1&api_key=…`，弹层里出现两行候选（`沙丘` 2021 · 电影 · 简介、`绝命毒师` 2008 · 剧集 · 简介），状态行写「找到 2 条结果，点一行关联到这条影视。」
- 点「沙丘」那行：服务端收到 `GET /tmdb/3/movie/693124?language=zh-CN&append_to_response=credits`；弹层关闭、Toast「已关联《沙丘》」，详情页立刻是 沙丘 + 2021 + TMDB★8.1 + 科幻 / 冒险 + 导演 / 主演 + 简介；退回首页，那张卡已经是「沙丘 / 2021 / 8.1」——就是这次报上来的那个现象。
- 再进详情页点「自定义编辑」，六个框预填刮削结果；片名改成 `沙丘_IMAX` 保存，详情页与首页卡片都跟着改。
- 整库再扫一轮：横幅收尾「刮削完成，共处理 45 个条目。」——46 个条目里那个手动匹配过的没被再刮，改名也没被覆盖。

跨类型改绑（在剧集上关联一条电影）这条路径在模拟器上没验：那需要一个带 `SxxExx` 的文件名，临时库里没有。真机上如果碰到，症状会是「关联后详情页跳回另一部片子」，那正是换表重建后条目 id 变了。
