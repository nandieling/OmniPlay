# 2026-10-12 · 中文译名补链、年份按 mac 重取、八套主题重画（1.29）

## 这一轮的五件事

用户对着真机提了五条：详情页别再折叠简介、右上角那颗手动匹配图标没画好、部分影视刮成了英文、自动匹配的年份取错了、手动匹配弹窗里那句提示是多余的。外加一句「几款主题都还不够好看」。前五条都有明确的对错，第六条只能拿截图说话，所以两条线分开做：先把功能两条（中文译名、年份）落到与 mac 版同一口径，再把八套色板整轮重调。

## 外文片名换中文译名

TMDB 的行为是：某个条目没有中文语言版本时，直接把原文名当 `title` 回传。于是刮削结果里留下 `Inception`、`Christopher Nolan`，首页卡片和详情页跟着一起变英文。mac 版早就为这件事写了 `ChineseNameStore` + `TMDBService.fetchChineseTitle`，这一版把同一条链路搬到 TV：

```java
// LocalEngine：拿到资料、写完入库记录之后顺手问一次别名
localizeTitle(mediaType, entityId, result.id, result.title, deadlineAt);
```

`TmdbClient.fetchChineseTitle()` 打 `/{movie|tv}/{id}/alternative_titles`，返回 `ChineseTitleResult{title, requestFailed}`。挑法与 mac 一致：电影别名在 `titles`、剧集在 `results`，两处并进一张清单，先按 CN → SG → TW → HK 找带汉字的地区译名，四个地区都没有就退到清单里任意一条含汉字的条目。404 是「这部作品确实没有别名页」，算明确答案；连接失败只是这次没问上，不能记成没有。

三个地方特意与 mac 对齐：

- **只改 `title`，不动 `isLocked`。** 手动匹配过的条目照样该显示中文片名，「锁定」挡的是自动刮削覆盖，不是本地化。
- **刮削语言选 English 时整条链路跳过**（`!"zh-CN".equals(tmdb.language())` 直接返回）。英文界面留原文名才对。
- **正缓存一直用，负缓存 30 天。** 新表 `chineseNameCache(key, title, updatedAt)`，`title` 为空就是负缓存，30 天内不再重复问；TMDB 后补的中文条目一个月后自然会被再问一次。这条时间窗与 mac 版 `ChineseNameStore` 同一个值。

老库里那些早就刮成英文的条目也要能翻过来，所以刮削收尾加了一遍补偿：`library.localizationCandidates(40)` 用一条 SQL 挑「已刮削、有 tmdbId、片名不含汉字、别名没查过（或负缓存已过期）」的条目，一轮最多 40 条，进度写一行「补中文译名：Inception」，收尾报「补了 N 个中文译名。」。负缓存正是为这一遍准备的，否则每次总结都要把没中文的片子重问一遍。

### 表加了，装过旧版本的机器上却没有

`chineseNameCache` 建在 `onCreate` 里，第一次查缓存就抛 `no such table`，异常被刮削循环外层的 `catch` 吞掉，那条条目记成「请求失败」——表现是刮得动、海报也出、状态一切正常，就是不换中文名。`onCreate` 只在数据库第一次建立时跑，`onUpgrade` 只在版本号变化时跑，两处都会路过的那句 `onCreate(db)` 也就跟着不会跑。数据库版本号提到 3，`onUpgrade` 里补一段 `if (oldVersion < 3)` 建表。

### 别名请求的 URL 拼错了一次

`apiKeyQuery()` 返回的是 `&api_key=…`，那是给已经带查询串的 URL 用的；`alternative_titles` 这条路径原本没有 `?`，拼出来就成了 `…/alternative_titles&api_key=xxx`，服务器回 400，看不出来。改成 `apiKeyQuery(true)`（`?` 打头那版）。假服务器的访问日志是唯一能抓住这类错的东西——真机上它只表现为「中文名就是不换」。

顺带记一句：搜索请求里从来没有 `year` 参数，假服务器日志里的 `year=''` 不是 bug。年份只喂给本地的 `score()` 与 `isYearPlausible()` 做校验。

## 年份按 mac 的取法重来

上一版取的是「文件名里最大的那个四位数」。`Toy.Story.1995.2010.720p` 记成 2010，按年份建的目录（`2024/某片.2019.mkv`）记成 2024——片名自带的年份永远抢不过后面那些重制与发行年份，年份校验于是把一批本该通过的匹配判成「年份对不上」。

现在照 mac 版 `chooseReleaseYear(from:)`：取**第一个**前后都不接数字、落在 1900–2099 的四位数；只有一个例外——文件名开头就是第一个候选（`2012.2009.1080p.mkv` 这种片名本身是个年份的写法），年份取第二个。

```java
private static final Pattern YEAR_PATTERN = Pattern.compile("(?<![0-9])((19|20)\d{2})(?![0-9])");
```

十组用例逐条过（一个临时 harness：拿 JDK 直接编译 `LocalMediaNameParser` + `UrlLabels` 与一张用例表跑 `main`，打印 `ALL PASS`）：

| 文件名 | 取到的年份 |
| --- | --- |
| `Toy.Story.1995.2010.720p.mkv` | 1995 |
| `2012.2009.1080p` | 2009 |
| `Inception (2010) [tt12345] [2010]` | 2010 |
| `Blade.Runner.2049.2017.2160p` | 2049 |
| `2001.A.Space.Odyssey.1968` | 1968 |
| `Some.Show.S01E02.2019.1080p` | 2019 |
| `NoYearHere.1080p.x264` / `Movie.12010.720p` | 无 |

`Blade.Runner.2049.2017` 取 2049、`2001.A.Space.Odyssey.1968` 取 1968 这两条我一开始的期望值写错了：按「片名自带年份会被后面的发行年份抢掉」的旧规则，直觉会写 2017 和 2001，而 mac 那套取法给出的正是 2049 和 1968——`Blade Runner 2049` 的 2049 是片名，1968 才是《2001 太空漫游》的年份。用例是拿去核对 mac 行为的，不是核对直觉的。

改的时候踩了一处坑，值得单独记：`YEAR_PATTERN` 只有一个捕获组（`(19|20)` 那个是内层），我按两组取值读了 `m.group(2)`，`IndexOutOfBoundsException` 从 `registerFile` 往外抛，`scanAll` 接住后写成「扫描失败：null」，界面上只是海报一动不动。真机表现为「扫描出了文件但一个都没入库」，靠单测 harness 才定位到。取 `m.group(1)`。

## 八套主题重画

浅色五套原本是把 mac 的色值原样搬过来的，投影仪和电视上看就是一屏发灰：纯白卡片贴在接近纯白的底上分不出层，副标题灰到三米外读不清。这轮每套都重调了六个色值，并各自多带一个 `wash`：

| 主题 | 强调色 | 底色 | 卡片色 | 副文字 | wash |
| --- | --- | --- | --- | --- | --- |
| 原生经典 | `#0A7AFF` | `#F1F2F6` | `#FFFFFF` | `#86868E` | `#E6EBF5` |
| 晶透白 | `#0A84FF` | `#F7F9FC` | `#FFFFFF` | `#5C6572` | `#E4EFFF` |
| 亚麻灰 | `#0F8F83` | `#F4F3F0` | `#FCFCFA` | `#6B7280` | `#E7E4DC` |
| 薄荷清 | `#0F9F6E` | `#EFF6F3` | `#FFFFFF` | `#557F72` | `#DBEFE4` |
| 北欧粉 | `#DB2777` | `#FCF3F7` | `#FFFFFF` | `#96657A` | `#F9DFEA` |
| 午夜蓝 | `#6BA5FF` | `#070D1A` | `#121B2C` | `#93A6C0` | `#102347` |
| 石墨黑 | `#34D3B0` | `#101113` | `#1C1E22` | `#99A0AA` | `#1A2126` |
| 纯黑 | `#0A84FF` | `#000000` | `#0C0D10` | `#94919C` | `#060A14` |

背景渐变不再是从左上到右下两色对拉，而是四段停靠点：左上角只是「底色掺一点 wash」，中间一大段保持纯底色，右下角才让强调色显出来。

```java
return new GradientDrawable(GradientDrawable.Orientation.TL_BR, new int[]{
        blend(BACKGROUND, WASH, 0.55f), BACKGROUND, BACKGROUND,
        blend(WASH, ACCENT, DARK ? 0.30f : 0.22f)});
```

中间那两段都是纯底色是故意的：两色对拉的渐变在电视上会把整屏染成一层灰，海报颜色跟着发闷。副文字统一压深到 4.5:1 以上，深色两套的 wash 与底色拉开了更大距离，关灯观影时能看出层次但不出光斑。

设置里那颗小色块也从「一块卡片色 + 一条强调色」换成迷你页面缩影：三停渐变当底、 inset 一张卡片、卡片上再压一条强调色条，34×20dp。八套摆在一起能直接看出差别，选主题不用再靠试。

## 详情页与弹窗两处收拢

简介不再按 96 字折叠（`setMaxLines(24)` + 删掉「展开简介」那一块）：电视上一屏就放得下，多一颗按钮只是多一次按键、多一处焦点跳不到的地方。

手动匹配弹层里那句「找到 N 条结果，点一行关联到这条影视。」撤掉，只在「正在请求 / 请先填关键词 / 搜索失败 / 没找到」这些真正需要说明的状态下显示。省下来的高度正好多摆一条候选。

右上角那颗 `text.magnifyingglass` 重画：三行长短递降的文字压在左上，放大镜落在右下，圆周先在独立图层上用 `PorterDuff.CLEAR` 抠掉一圈再画镜筒（与 `watched` 图标同一手法）。不抠这一圈，22dp 下镜圈和文字笔画会粘成一团。

## 验证

模拟器（1080p Android TV 镜像）+ 假 WebDAV（`:8100`，目录树把文件同时摆在挂载根和 `Movies/`、`Documentary/` 下，每条 207 响应带头「目录自己」那一条）+ 假 TMDB（`:8099`，`/search/multi` 按查询词回外文库名、`/{kind}/{id}` 回详情、`alternative_titles` 回一条 `iso_3166_1: CN` 别名，统一记访问日志）：

- 走完整挂载流程后 `扫描完成` 登记 7 个文件（根目录与子目录各若干）——**这一条是本轮回归的门禁**，年份正则那个越界异常就是让它先红起来的：海报墙全空、左上角一句「扫描失败：null」。
- 海报墙先出外文库名，刮完变 `中文译名1048` / `中文译名1362` / `中文译名308`，假服务器日志里对应三次 `ALT` 请求。第二遍扫描不再多发别名请求（正缓存挡住）。
- 假服务器所有结果都回 2010 年：`Toy.Story.1995.2010` 按 1995 判为年份对不上、留在未刮削，`Inception (2010)` 正常通过。用旧的「取最大四位数」规则，前者会被记成 2010 而错误匹配——这一条正好证明新取法生效。
- 详情页简介整段显示、无折叠按钮；手动匹配弹层无提示行、候选带海报；图标裁出来放大核对过。
- 八套主题逐一切换截图，深色两套在关灯环境下对比正常。

真机才暴露的三个问题——缺表、URL 拼错、正则分组——都不是看截图发现的，是假服务器日志和单测 harness 逼出来的。
