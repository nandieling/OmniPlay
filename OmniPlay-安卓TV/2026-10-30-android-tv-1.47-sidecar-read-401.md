# 2026-10-30 · 1.47：转档出来的字幕读不回来，是 HTTP 401

## 一、现象

高性能直出下打开字幕弹窗，NAS 那台「字幕转档」写在片子旁边的 `.sup` 与 `.srt` 都列得出来，点一条，电视只回一句：

```
读取字幕文件返回 HTTP 401
```

「列得出、读不回」这个组合本身就是线索：两条路走的不是同一套凭据。

## 二、根因

WebDAV 侧有三条取文件的路，只有一条带了账号。

- 列目录：`WebDavClient.list()` 自己塞了 `Authorization: Basic …`（`credential.cookieHeader`），所以 sidecar 能被认出来。
- 播放视频：`WebDavClient.streamUrl()` 把账号拼进 URL 的 userinfo（`http://user:pass@host/dav/…`），交给 mpv，mpv 认这套，会自己换成 Basic 头。
- 读 sidecar：`SubtitleSidecarService.WebDavAccess.read()` 把同一个 `streamUrl()` 交给我们自己那个走 socket 的 `Http` 客户端——而 `Http.Target.parse()` 里取的是 `parsed.getHost()`，**userinfo 解析完就丢了**，请求等于匿名发出去。受保护的共享回 401，`read()` 就抛那一句。

同一个 `WebDavAccess` 里的 `exists()`（HEAD）、`length()`（HEAD）、`write()`（PUT）、`writeFile()`（流式 PUT）、以及 `open()` 出来的 `HttpRangeSource`（探内封轨时读 EBML 头）全是一样的写法，也就是说这台转档服务在受保护的共享上其实一直只能"列"不能"读写"：转档回写、续跑时拉回前半段、当场抽内封文本轨，都会静默失败或报奇怪的 HTTP 码。

## 三、改法

两层都补，别只补一处。

`Http`（根因那层）：`Target` 带上 `userInfo`，请求头里没有 `Authorization` 时按它补一条 Basic；调用方自己给了就以调用方的为准（`hasAuthorization` 大小写不敏感）。userinfo 是按 URL 编码拼进去的，先解回原样再算 Base64，否则密码里有 `:` `@` `/` 就会拿编码串去认证、照样 401。Base64 用 `java.util.Base64`：minSdk 26 起有，JVM 自检也不用拖 `android.util` 的桩类。

```java
String inherited = target.userInfo.isEmpty() || hasAuthorization(headers)
        ? null : basicAuth(target.userInfo);
if (inherited != null) {
    request.append("Authorization: ").append(inherited).append("\r\n");
}
```

`WebDavAccess`（本地那层）：新增 `authHeaders()`，read / HEAD / PUT / 流式 PUT / Range 一律显式带上 `client.authorization()`。这层不是重复劳动——`streamUrl()` 只在「账号非空」时才拼 userinfo，显式带凭据能保证 URL 因故没带上凭据时也不退化成匿名请求。`HttpRangeSource` 相应加了一个 `(url, baseHeaders)` 构造，Range 往基础头上面加。

`WebDavClient.Credential` 顺手从 `android.util.Base64` 换成 `java.util.Base64`（编码结果一样，都是不换行），这样自检里能真的构造带账号的 `WebDavAccess`。

提示语也别再只报个码：401 / 403 会说「媒体源的账号读不到这个文件（共享可能是只读或换了凭据），重新登录一次媒体源再看」。

## 四、验证

`build/harness/SidecarCheck.java` 里那台 `HttpServer` 加了一道门：`/dav/locked/` 下的条目只放行者是 `omni:se@cret`（密码故意带 `@`，就是为压 userinfo 编解码这条），其余一律 401。补的 5 项：

- 未授权读 `/dav/locked/…` 必须回 401（否则下面几条是白测，自检会把这条真实消息打出来）；
- 带账号的 `WebDavAccess.read()` 读得出转档产物；
- 带账号的 Range 探测能读到 MKV 头并认出 3 条字幕轨；
- 带账号的 HEAD 认已存在的 sidecar；
- 带账号的 PUT 写得进。

```
（未授权的读取报的：读字幕文件返回 HTTP 401，媒体源的账号读不到这个文件（共享可能是只读或换了凭据），重新登录一次媒体源再看。）
OK 字幕转档 51 项全部通过
OK 手机字幕 13 项全部通过
```

`zsh build/tvtools/compile.sh` 通过。走 socket 的 `Http` 只有 WebDAV 用，SMB 走 `SmbClient`（账号在 `SmbClient` 里）、本地目录走文件，都不受影响；`LanDiscovery` 那些探测 URL 不含 userinfo，401 判定不会被这条改变。

真机没在 MAS 上复现：那边没有配好的 WebDAV 媒体源，要压这条得先起一台带 Basic 认证的 WebDAV，成本高且与自检覆盖的是同一段代码，所以以自检这 5 项为准。手上那台 NAS 上是现成的复现环境，装 1.47 后点同一部片的 `.sup` / `.srt` 就能对照。

## 五、留给下次的两句话

同类问题在 `OfflineCacheManager.openInput()` / `expectedSize()` 里还有一份：它们也是从 URL 取 userinfo 拼 Basic，但没做 URL 解码，密码带特殊字符就会认证失败。这块 1.15 起 TV 端不再提供、`cache()` 目前没有调用方，属于休眠代码，等哪天真要恢复离线缓存再一起收拾，别顺手改一片。

再加一条口径：以后凡是「把凭据拼进 URL 交给别人」的地方，都要明确那个别人认不认 userinfo——mpv 认，`Http` 以前不认。要么像现在这样两头都带，要么干脆只走请求头，别留一条靠 URL、一条靠请求头的分裂写法。
