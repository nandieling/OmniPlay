# 2026-10-15 字幕转档瘦身版

## 为什么单开一份

上一轮把内封字幕后台转档做进了安卓 TV 端（v1.34）：电视自己用 Java 写的 Matroska 抽取器
把 MKV 里的字幕抽成 `片名.zh.srt|ass|sup` 写回媒体源。真机讨论下来有两点不合适长期这么跑：

- 电视端读整条轨要顺序读完整个文件，走网络时占的是电视的 CPU 和那根网线；
- `.m2ts` / `.ts` / `.iso` 这类容器电视端的抽取器覆盖不到。

于是把「批量、全量、闲时跑」这件事挪到 NAS。`OmniPlay-docker` 里已经有 ffmpeg 和字幕缓存服务，
但它是个完整媒体服务器，用户反馈功能太多、镜像太大，所以另开一个只做转档的文件夹。

## 选型

`OmniPlay-字幕转档/`，一个 Python 3 标准库脚本 + ffmpeg：

- 探测用 `ffprobe -show_streams`，抽取用 `ffmpeg -map 0:s:N`，不自己写容器解析器；
- 状态表用 sqlite（标准库自带），记状态、进度、失败原因、重试次数，重启不重做；
- HTTP 用 `ThreadingHTTPServer`，页面是手写的一张任务表，不引前端框架；
- 镜像 `alpine + python3 + ffmpeg`，比 .NET + Node + 字体那套小一大截。

## 关键取舍

**主动扫库只碰 MKV/WebM/MP4。** 蓝光目录里 `00000.m2ts` 排成一片，哪条是正片只有 TV 端扫描
逻辑知道（它按主片规则挑过），NAS 不知道，所以这类容器只走 `POST /api/jobs` 点名，
由电视端把真正要放的那条推过来。

**一个视频一次只转一条字幕。** `--langs` 是偏好顺序而不是「全都要」：命中第一条就收工。
理由是同语言的多条轨（国/粤都归一成 `zh`）输出路径会撞车，而 sidecar 的价值就在播放时
读那一条；真要双语，两条语言分开跑或者人手再点一次。

**已有外挂字幕就跳过，且只用目录列举判断。** 扫描时每个目录列一次文件名，看有没有
`片名.xx.srt|ass|sup`，有就整条跳过。这样对人手放字幕、TV 端写的、上一轮自己写的产物一视同仁，
也不用为判断去读文件内容。

**写回走临时文件再 rename。** 全量跑的时候难免断电、断网、被人手动中止，
半个 `.sup` 留在片旁边比没有字幕更糟——播放器会挑它，然后显示不出东西。

## 验证

`python3 selftest.py`（本机 ffmpeg 9.0.1）：真视频 + 中文 SRT + 英文 ASS 的 MKV、带现成 sidecar 的 MKV、
无字幕 MKV、只读目录里的 MKV，跑完核对：

- `大电影.2019.1080p.zh.srt` 生成，两句中文和 `00:00:05,500 --> 00:00:08,000` 时间轴都在；
- 已有字幕的那条判「已有字幕」，没字幕的判「转不了」，只读目录的判「写不回去」；
- 扫第二遍队列里 0 条；
- `/health`、页面、`/api/jobs`、`POST /api/jobs`（路径越界和不存在的一律挡掉）、`/api/scan`；
- 带 `--token` 时不带令牌 401，带对令牌 200。

20 项全过。GUI 用内置浏览器实际看过一遍：状态卡、分段筛选、搜索、手动转档、任务表、
重试按钮都渲染正常，点「扫描媒体库」服务端日志确实多了一行扫描记录。

PGS 那一条自检里是「跳过」而不是「通过」：本机没有真蓝光片源，手搓的 MPEG-TS 里
`stream_type=0x90` ffmpeg 不认（试了 0x83/0x90/0x92/0x06、加 0x6A/0x6B/0x64 描述符都一样，
`-show_streams` 始终报 unknown），所以那条链路的代码写了但没被真片验证。
上 NAS 拿一张真蓝光的 `.m2ts` 点一次名就算补上。

顺带记两个坑：

- 首页路由原来写的是 `if route in ("", "/index.html")`，而 route 是 `path.rstrip("/") or "/"`
  算出来的，`/` 永远变成 `"/"`，结果首页 404。
- 本机挂着系统代理（127.0.0.1:1082）时，自检客户端会被代理拦下返回 503，
  跟服务端没关系。客户端一律换成 `ProxyHandler({})` 的直连 opener。

## 群晖套件版

有人不想在 NAS 上跑容器，那就再给一条路：装成群晖套件。`synology/` 下放的是打包源料，
`./synology/build-spk.sh` 产 `dist/OmniPlaySidecar_1.0-1_noarch.spk`，21 KB。

包结构照 DSM7 的约定：`.spk` 外层是 `INFO` + `conf` + 两张图标 + `package.tgz`；
`package.tgz` 里是 `info` / `conf` / `scripts/` / `target/`，DSM 把它解到
`/var/packages/OmniPlaySidecar/` 下面。起停用 systemd 单元（`Type=forking` + `PIDFile`），
同时留着 `scripts/start-stop-status` 给老接口。配置和进度表放 `.../var`，
升级只换 `target`，所以改过的配置不会被覆盖。

三个决定：

- **不自带 ffmpeg**。Synology 上 ffmpeg 是社区包（`ffmpeg8` 之类），装在
  `/var/packages/ffmpeg8/target/bin`，脚本按 ffmpeg8/6/4、MediaServer、`/opt/bin`、`/usr/local/bin`
  的顺序找，也允许在配置里写死。硬塞一个静态 ffmpeg 会让 21 KB 的包变成几十 MB。
- **以 root 运行**。要往媒体库目录里写文件，那目录是 root/admin 的；套件里专门声明一个系统用户
  反而要再处理属组，不值当。
- **不带安装向导**。Wizard 是 XML，为了两个路径字段不值当；改成装完编辑
  `.../var/sidecar.conf`，`postinstall` 会把这句话打给用户。

验证：`synology/dryrun.sh` 在电脑上按同样的目录结构把装/起/状态/health/停走了一遍，
全通过，顺带把「没装 ffmpeg 时只警告不报错」这条路径也走出来了。真 NAS 上没装过，
`info` 的字段是照社区包那份抄的，不确定的字段（`restart_auto`、`package_support`）已经删掉，
只留确定存在的。图标由 `synology/makeicon.py` 现场画（纯 zlib 写 PNG，不引图像库），
深绿圆角底 + 底下两条字幕条，跟管理页面同一个强调色。

## 装上才暴露的一件事：apk 源

第一次在 SA6400 上 `docker compose up -d --build` 挂在 `apk add` 上：

    WARNING: fetching https://dl-cdn.alpinelinux.org/alpine/v3.20/main: temporary error
    ERROR: unable to select packages: ffmpeg (no such package)

镜像能拉（Docker Hub 那步走通了 registry 镜像），但 `dl-cdn.alpinelinux.org` 这个 Fastly 的
CDN 连不上，APKINDEX 取不到，于是三个包全报「没有这个包」。Dockerfile 把源做成构建参数
`ALPINE_MIRROR`，`compose.yml` 默认填阿里云，清华和中科大写在注释里备选；三个源都不通就换机器
`docker build` + `docker save`，或者走群晖套件那条路。顺手把上一版的 `cpu_weight: 256` 删了——
那是 Swarm 的字段，Compose 校验直接拒。

换成清华源之后 sed 那步是过去了，紧接着又炸在下一句：

    apk: unrecognized option: retry

`apk add --retry 3` 是我凭空写的——apk-tools 2.14 只有 `--timeout`（网络连接多久没进展就放弃）
和 `--wait`（等仓库锁），没有 `--retry`。加重试得自己在 shell 里写循环：

    RUN sed -i "s|...|${ALPINE_MIRROR}|g" /etc/apk/repositories \
        && tries=0 \
        && until apk add --no-cache --timeout 60 python3 ffmpeg tzdata; do \
             tries=$((tries + 1)); \
             [ "${tries}" -ge 3 ] && exit 1; \
             echo "第 ${tries} 次没装上，5 秒后重试"; sleep 5; \
           done

`until` 的语义是「命令失败就一直进循环体」，所以装成功就正常往下走；两次都失败第三次仍失败时
`exit 1` 让构建停下来，不会默默产出一个缺 ffmpeg 的镜像。用 `/bin/sh` 单独跑过两遍确认：
一直失败 → exit 1；第二次成功 → 继续往下执行。

## 换源之后才看清：那台机器压根没走我们指定的源

重试循环按设计跑了三轮，但每一轮抓的都是 `https://mirrors.ustc.edu.cn/alpine/...`——
不是传进去的清华源。原因在基镜：从国内加速站拉下来的 `alpine:3.20`（这次 digest
`ed1b3f7f`，跟第一次的 `d9e853e8` 不是同一份）里，`/etc/apk/repositories` 已经被站点改成
自己的源了，而我那句 sed 找的是 `dl-cdn.alpinelinux.org`，匹配不上，于是整条换源命令一声不响
地什么也没干，构建容器里外网又不通（ustc 五次都是 5 秒报 `temporary error`，Docker Hub 那步
却走通了加速地址），三个包继续报「没有这个包」。

所以换成了「覆写整个 repositories 文件 + 挨个试五个源」：版本号从 `/etc/os-release` 现取，
候选是 `ALPINE_MIRROR`、阿里云、清华、中科大、官方 CDN，第一个 `apk add` 成功就停。用桩函数
`apk` 在本机验过三种情况：前两个不通 → 第三个接上；第一个就通 → 不再往下试；全不通 → exit 1
并提示换 `--build-arg` 或开 `build.network: host`。顺手记一笔：`apk add --retry` 这个选项
根本不存在（2.14 的 help 里只有 `--timeout` 和 `--wait`），重试必须自己写循环。

再往后是两条不跟 apk 较劲的路：构建加 `--network=host`（容器内 DNS 才是嫌疑犯，宿主机
`curl` 一下 APKINDEX 就能分辨）；或者用新的 `Dockerfile.noapk`，基镜换成自带 python3 的
`python:3.12-slim`，构建过程零外部请求，ffmpeg 不装进镜像、把群晖套件的整个 target 目录挂到
`/opt/ffmpeg`。这条特意选了 Debian 基镜——群晖套件里的 ffmpeg 是 glibc 编的，塞进 musl 的
alpine 起不来。它和 SPK 一样都还没在真机上验过。

## 通网之后立刻露馅：仓库路径拼错了

`--network=host` 一加，五个源全在 1 秒内回了真话：`No such file or directory`。抓的是
`.../alpine/v3.20.10/main/...`——我拿 `/etc/os-release` 的 `VERSION_ID` 拼仓库路径，而小版本
镜像里那个值是 `3.20.10`，apk 仓库只按分支发（`v3.20`），点版本目录压根不存在。改成只取前两段
（`major` + `rest%%.*`），顺带把候选列表去重：`ALPINE_MIRROR` 和内置候选撞上就不再重复试第二遍。
用桩函数把 `VERSION_ID` 设成 `3.20` / `3.20.10` / `3.22.1` 各跑一遍，拼出来都是 `v3.20/main`、
`v3.20/main`、`v3.22/main`；再把前几个源标成不通，验证退路链和「四个源全失败 → exit 1」。

这一轮反倒确认了网络是好的：错误从 `temporary error` 变成了秒回的 404。

## 装上之后要的三件事：翻页、挑着转、别看爆盘

真机跑起来第一轮的反馈很实在：列表一屏翻不到底、1080p 根本不需要转、盘快满了没人喊停。

- 列表改成服务端翻页与筛选（`page` / `per_page` / `status` / `q` / `res`），旧的
  `limit=` 仍然认。浏览器只拿当前那一页，几万条也不卡。
- 探测时顺手记下视频分辨率（`ffprobe` 的 JSON 里就有），存进 `jobs.width/height`，
  老库靠 `ALTER TABLE` 补列。`--min-height` 是道闸门：低分辨率的判成「按策略不转」。
  闸门只管还没干过活的片源——已经转好的不倒退，改过阈值时把旧判定抹掉等下次重扫。
- 每个媒体库一份 `shutil.disk_usage`，`--min-free-gb` 跌破就暂停往里写：任务留在队列里
  不消耗，页面上磁盘卡片变红加一行横幅，腾出空间自动接着跑。
- 这两个值都能从页面上改，存进 `settings` 表，盖在环境变量默认值之上。

自检从 20 项加到 27 项，新加的都在验这些：翻页取第二页不与第一页重复、按分辨率筛、
策略改动的 `cleared` 语义、阈值调到天上就报 `paused`，以及「72p 按策略跳过且不落产物、
不设阈值就照常转」。页面在浏览器里点过一遍：4K 筛出空列表、阈值 21 GB 时磁盘卡片与横幅
都变红。

## 少敲一个参数就会再撞一次

分支修对之后（日志里已是 `v3.20`），下一条日志又是五个源齐刷刷 5 秒 `temporary error`——
这回不是源的问题：用户敲的是 `docker compose up -d --build`，没带 `--network=host`，而
`ip_forward=0` 那台机器上 bridge 里的构建容器压根出不去。既然这台机器每次都得走宿主机网络，
就别再指望记参数了：`compose.yml` 里把 `build.network: host` 打开（注释掉的那行扶正），
`docker compose up -d --build` 从此自带。真撞上老版 compose 不认这个键，退回
`docker build --network=host -t omniplay-sidecar:latest .` 再 `up -d` 也一样。

## 别一容器起来就抢盘

再往上是使用习惯的问题：容器随 DSM 自启，起来就闷头扫全库、抽字幕，谁都不知道。现在加了
一道闸门：`Service.running` 默认 False，worker 卡在 `gate` 上、ticker 直接跳过，页面上
「开始转档 / 暂停」就是 `POST /api/run`。开闸顺手 `scan_now.set()`，不用等下一个
`--interval`。`--once` 那条路（cron / systemd timer 用的）绕开闸门，本来就是「明说了就跑」。

`--min-free-gb` 默认值从 0 改成 500，页面上也从固定档位换成可填的数字——几百 TB 的池子和
两块的盘子要的阈值根本不是一个量级，给下拉框不如给个框。「空间不够」和「你按了暂停」是两件
不同的事，所以 `/health` 里分开成 `state` 和 `disk_blocked`，页面上状态灯分三色。
自检加到 35 项：暂停时扫描只排队不开工、不认识的 action 报 400、不带 `--autostart` 起来就是
停着的、默认阈值读出来是 500（这条要拿一份全新的状态表验，上一轮在页面上存过的策略会盖掉
默认值，那正是应有的行为）。

## 数字填一半就被轮询抹掉

`refresh()` 每 3 秒把服务端策略回填进表单，输入框也在回填之列：数字刚敲进去，下一轮轮询
就把已保存的值盖回来（默认那会儿是 500，之前存过 0 就直接归零），看着像输入框自己坏了。
改成回填时跳过「正被编辑」的那个——`document.activeElement` 或者标了 `dirty` 的都跳过，
`input` 事件负责打这个标，保存成功后清标并按返回值重新回填。顺手把「改过没保存」显出来：
按钮变成「保存策略（未保存）」并描一圈主色，输入框里回车就等于点保存。

在浏览器里验过：往阈值框里填 120，等 7 秒（两轮多轮询）数字还在，按钮已是未保存态；
改成 0 点保存，弹出「策略已保存」，磁盘卡片同时从红色阈值态回到正常的
「剩 20.0 GB / 共 228.3 GB」，暂停横幅按运行状态留着——三件事各自说话，互不串台。

## 点了「开始转档」什么也没发生

真机反馈：顶上按了开始，下面列表空着。翻 ticker 的代码才看出来是我上一轮埋的雷——
那个循环里 `self.scan_now.clear()` 放在循环体末尾，暂停时内层 `while self.running and …`
条件立刻为假，于是外层**一秒都不睡地空转**，顺带每圈把唤醒标记清一次。你点「开始转档」
`set_running(True)` 刚把 `scan_now` 立起来，就被这个空转圈抹掉了，ticker 于是老老实实在
`--interval`（默认 900 秒）之后才扫第一遍。空转本身还白烧一个核。

改成：暂停时 `scan_now.wait(2)` 阻塞等唤醒、不清标记；开始后先扫，再
`scan_now.wait(interval)`，`--interval 0` 就是 `wait(None)` 睡到有人按扫描/开始。
顺带把「一开始就扫第一遍」从 `main()` 挪进 ticker——之前 `--interval 0` 是在 `main()`
里直接扫的，绕开了闸门，暂停状态也照扫，跟「暂停就是不动手」自相矛盾；现在线程一直起，
第一遍由它在闸门打开后跑。

`walk()` 外面套了个 `self.scanning`，`/health` 里报出来，页面上状态灯写成
「正在扫描媒体库…」——之前点了开始只剩一句「正在跑」，大库扫上几分钟，看着就像没反应。

自检里那条 regression 是这么写的：把间隔设成 3000 秒，起服务时不带 `--autostart`，
断言起来是停着的、`stats.scans` 是 0；点 start 之后最多等 10 秒，`stats.scans` 必须变 1。
不修这个 bug 它就一直红。顺手在真机同款配置下看了一眼：暂停态 `ps` 读出来 CPU 0.0%，
不烧核了。

## 顶上「转不了」有 3 条，下面却找不着那条

第一版把状态分段按钮（全部 / 待转 / 转档中 / 已完成 / 异常 / 跳过）和计数格分开画，
`异常` 混了失败+只读，`跳过` 又把「转不了」和「已有字幕」揉在一格。于是顶上明明写着
转不了 3 条，下面无论点哪个分段都凑不出那 3 行——数字和列表说的不是同一件事。

干脆把计数格本身变成筛选项：一格一状态（`STATUS_GROUPS` 一一对应），格子上加
`aria-pressed`，点谁谁亮，列表跟着走，第一格「全部」显示总数。原来那排分段按钮删掉。
服务端顺手把 unsupported 和 skipped 拆成两个独立分组，`skipped` 的行里再用状态条区分
`已有字幕` / `按策略不转`，两种「不转」不再长得一样。

顺带一个手感的坑：计数格原先每 3 秒 `innerHTML` 重建一次，鼠标点下去刚好赶上重建就
点了个寂寞（用无障碍树点时也复现过「目标已经不在 DOM 里」）。改成格子只建一次、
之后就地改数字和选中态，点起来就稳了。

自检加了一条：挨个用 `?status=<单个状态>` 请求，要求返回的行全是那个状态、`total`
等于 `/api/jobs` 里那一格的计数，且七格加起来等于全量——少一格、串一格都会红。
